# Project notes

Procurement Intelligence prototype for manufacturing SMEs. See README.md (Italian) for setup and architecture.

- All business numbers are computed in `src/lib/analytics.ts` (pure functions, tested). Never store derived values (current price, price history, spend) in the database.
- All writes of the workspace go through `src/app/actions.ts` and `src/app/order-actions.ts` (or an importer with preview → approval); the supplier portal writes through `/portal/api` only. Validation schemas live in `src/lib/validation.ts`.
- Schema changes: edit `src/db/schema.ts`, then `npm run db:generate`; migrations in `drizzle/` apply on startup.
- Two languages, English and Italian (`src/lib/i18n/`). The English text written in the code is the key; its Italian lives in `src/lib/i18n/it/*.ts`, and a text missing there does not compile (`Msg`). Never put user-facing text in the UI or in an engine without going through the translator: `await getT()` in server components, route handlers and actions (`lib/data.ts`), `useT()` in client components (`i18n/client.tsx`), a `t: T = en` argument in pure functions (English default, which is what the tests read). Label tables are typed `Msg` and translated where shown. Whole sentences, not fragments: `t("{n} lines ready", { n })`, `t.n(count, one, many)` for plurals, `rich()` when an element sits inside a sentence, `"Open|status"` when one English word has two meanings. The language is a setting (`settings.language`), changed from the top bar or Settings.
- Messages stored in the database (import issues, match reasons, file errors) are saved in English with their template and values (`say()`) and shown with `said(t, …)` / `t.any(…)`, so they follow the reader's language later.
- Numbers and dates use Italian formatting in both languages via `src/lib/format.ts`; month names and words like "days" go through the translator. Countries are compared with `countryKey()` and shown with `countryName()` (`lib/countries.ts`): "Italy" and "Italia" are the same place.
- Compare/alternatives must never rank or call a supplier "cheaper" until landed cost exists.
- Verify with `npm test`, `npm run typecheck`, `npm run lint`. Tests run in two groups (`vitest.config.mts`): `unit`, side by side, with timeouts sized for tests on an in-memory Postgres, then `scale` (`*.scale.test.ts`), the timings, alone — never time anything inside the `unit` group.
- Imports never write facts directly: file → import_items → user review/approval (`src/server/imports.ts`). Unit/currency/number/date parsing lives only in `src/lib/import/normalize/`; never guess an ambiguous value — flag it for review.
- Import scenarios: `test-data/` (regenerate with `npx tsx scripts/make-test-data.ts`); end-to-end tests in `src/server/imports.test.ts` run on in-memory PGlite.
- Price intelligence lives in `src/lib/intel/` (pure, tested): thresholds only in `config.ts`, explanations in `explain.ts`. Demo data is a test fixture — never shape logic around it; add generic cases to `src/lib/intel/fixtures.ts` tests instead.
- Savings vocabulary is strict: "price difference" (nominal) vs "potential saving" (estimate, price only) — never "saving realised", never "best supplier". No saving for non-comparable offers.
- Opportunities are computed by the engine; the `opportunities` table stores only the user's status/note/snapshot.
- The home page (`/`), the full review (`/report`), the product page and Compare all render `src/lib/intel/decision.ts` (summary engine: status, alternatives, next actions, plain-language text, priority). It selects and words what `analyze()` computed — no new price/saving formulas there, and no status or sentence worked out inside a React component.
- Supplier quality data does not exist yet. In the decision engine (`decision.ts`) `estimatedTrueCost` stays null and the market reference is `internal_quotes` or `not_available`: true cost and external evidence live in the sourcing module, with their own rules (below).
- UX rules (keep them): simple first, detail on demand. One global "+ Add" and one entry panel (`src/components/entry/`) — pages open it through `useEntry()` / the `*Dialog` buttons, never with their own form or option lists. Forms ask only what can't be inferred; optional fields go under `MoreDetails`. Secondary sections use `Disclosure`. One product status everywhere (`DecisionStatusPill`). Table columns are shown by container width (`@2xl:table-cell`…), not viewport. No jargon in labels (MOQ → "minimum order"); the technical term goes in a `Hint`. Never label a supplier best/winner/recommended to buy from ("recommended for a request for quotation" is the only recommendation the app makes).
- Imports: `createUpload(..., "auto", { autoMap: true })` from the UI; the service default stays explicit. Column guesses from values (header-less paste) are never applied without the user checking them.
- Not everything on an invoice is a product. `products.kind` (`src/lib/catalog/kinds.ts`) says what each item is: materials, components and packaging are the catalogue Procurement Intelligence works on (`getIntel()` runs on `catalogueOf(data)`); transport, services, utilities and the rest are company spend (`getSpend()`), one item per supplier and kind, never compared or watched for price changes. Supplier spend counts everything.
- Unknown products of an import are never asked one by one or created as written: `src/lib/catalog/propose.ts` groups them (pure, tested) and `src/server/catalog.ts` creates products only on the user's confirmation. Names alone never merge two products; a different number in the name keeps them apart unless the supplier's own code says otherwise, and then the user is asked. Classification is rule-based (`classify.ts`): add a word to the list of its kind; what the rules can't tell stays "to classify" and is asked — never guessed.
- Product Mapper (`src/lib/catalog/mapper.ts`, pure, tested; `src/server/mapper.ts` writes): reads the catalogue's products and proposes a readable name, category › subcategory (`taxonomy.ts`: add a word to its subcategory), family and variant, with a level — high (the name says it: bulk confirmation), medium (read from the supplier's context, or the name was shortened: shown to the user), low (asked). Possible duplicates are proposed, never merged by themselves; a different size is never a duplicate, a packing note ("60 pz. x scat") is not a size. It is a rule engine: no language model is called. Nothing is stored until the user confirms (`products.mapped_at`); categories, families and names are text the user can rewrite. A mapping never touches prices, quantities, suppliers or dates — a merge only moves purchases under the product that stays, and can be taken back. The page is "Product cleanup" (`/products/review`): how each product was read (original description, supplier, product, family, supplier's codes, confidence and why), the largest first.
- Product identity (`src/lib/catalog/identity.ts`, pure, tested; read by the mapper, the import matcher and the searches): who sold it is not what was bought, and what the supplier calls it is not what the product is. The description on an invoice is raw source data, kept as written (`product_aliases`, every purchase) and read apart each time — nothing of the reading is stored. Rules that must hold: (1) a word of the seller's own company name is the seller, not the product ("Paraffina SER 52/54" → "Paraffina 52/54"), unless it is also a word for a product, a material or a colour, and unless nothing but a model code would be left (a brand and its model stay as written); (2) the seller's codes are a short code in brackets, a bare number of five digits or more, the article code the document gives, and what stands in front of the noun after "ART." — they are listed as the supplier's codes and left out of the name whenever something else tells the product apart; grades, sizes and weights are the specification and are never touched; (3) every catalogue product has an identity: `named` (the words and the grade say what it is — the only ones confirmed in bulk), `supplier_code` (the words say the kind of thing and only the supplier's article code tells it apart: the code stays in the name, the group is "needs review" and one answer covers a supplier's range), `unidentified` (the words name a material that can be several things — a taxonomy subcategory with `ask` — and nothing says which: it keeps the name it has, gets no subcategory, and the user is offered at most three options, "something else" and "I don't know yet"; no name is ever made up from a code); (4) similar is not the same: two descriptions are the same product only when they name the same thing in the same grade (`compareIdentity`: same, likely, other_spec, unrelated) — another grade is another product of the same family and is never proposed as a match or a duplicate; (5) on import (`matchProduct`) the seller's own code read before on one of its descriptions is recognised when written again; the same identity from another supplier is a "probable" match the user links or keeps apart, never linked by itself; (6) a merge deletes nothing (`mergeProducts`): the rows that can follow (purchases, quotes, import lines, descriptions, candidates, benchmarks, research, documents) move under the product that stays and are logged in `product_merges`, the merged product stays on file with `merged_into_id` and is no longer listed (`readDataset`), and `undoProductMerge` puts everything back; (7) it is better to show "needs review" than to file a product wrong: nothing here optimises for having every product classified. No language model is called.
- Macro product and variants (`src/lib/catalog/macro.ts`, pure, tested; `confirmVariants` in `src/server/mapper.ts`; the cards "One product, several versions?" on `/products/review`): the structure is category › product family (the subcategory) › macro product (the row in `product_families`) › variant (`products.variant`) › supplier's product › description on the invoice. Fewer, cleaner products — never two different articles folded into one to tidy the catalogue. Rules that must hold: (1) articles are proposed as versions of one product only on evidence read together: the same supplier, the same unit, the same product family, names that begin (and may end) the same way with at most `maxVariantWords` words changing in between, and prices that sit together; a matching price supports it and never decides it — two names that do not begin alike are never tied by a price, and a price far from the others' (`priceBand`) leaves the article out, said in the card; (2) what changes is named only as far as the words say: a colour, a size or a capacity written in full is sure; an abbreviation (TR, BIA) is read as a colour only next to one written in full, on this article or on others of the same supplier, and said to be a reading; an ending nothing explains is shown as it is; (3) nothing is grouped by itself: every group has three answers — "they are variants" (the products stay apart, each with its purchases and price, filed under one macro product; what changes is asked and kept in `product_families.variant_by`), "merge" (one product written several ways: `mergeProducts`, which can be undone) and "keep separate" (not proposed again); a family the mapper already proposes is a macro product already and is not asked about twice, and a new version of a confirmed macro product is proposed next to the ones filed; (4) the same product written in another way is a possible duplicate, not a new product: the order of the words, a unit left out and a word cut short ("CONT LC TR 30" / "LC TR CONTENITORE 30 CL") — with the numbers in the same order, since "20x500 30 pz" is not "30x500 20 pz", and every letter counting, since "C5" is not "C5A". Names are split into words by `nameTokens` ("60L" = "60 L", "LC 1" = "LC1", "A B V" one code). Thresholds live in `MACRO_CONFIG`. No language model is called.
- One supplier, one day, two prices: two products (`src/lib/catalog/apart.ts`, pure, tested). The user's rule, with no exception: two descriptions billed by the same supplier on the same day at different unit prices are different products, however alike their names — a supplier does not bill one article twice on one day at two prices. It overrules every resemblance, everywhere: (1) such a pair is never proposed as a duplicate (`mapCatalogue`) and never joined or asked about among the new products of an import (`proposeProducts`); (2) a macro group that contains one can be confirmed as variants but is not offered for merging (`MacroGroup.mergeable`), and `mergeProducts` refuses it on the server whatever the caller; (3) in an import, a line that only resembles a product does not join it when another line of the same day is that product at another price (`keepApart`): it is asked about or proposed as new; (4) merges made before are checked against the invoices each time the cleanup page is read (`readProductMerges`): the contradicted ones are shown first, with what was billed and when, and taken back one by one or together (`undoProductMerges`) — a merged pair like this reads as a price increase that never happened. The same day at the same price says less (two colours often cost the same): it is said, it leans a group towards "variants", and it leaves the decision to the user. Prices closer than `SAME_PRICE` are one price written with more decimals.
- Supplier market research and requests by material (`.data/research/`, `src/server/research-files.ts`, `src/lib/sourcing/rfq.ts`): research done outside the app — by a person or by a session with web access — is kept as research files on the computer, one per material, each candidate with the page that shows it and each file with its `coverage` (the searches made, the sources read, the gaps): a research is never called complete beyond what its coverage shows, and a category with no candidate says why. The files are listed in the import box and loaded with the same check and confirmation as any other (`importResearch`): candidates to review, never suppliers. A request for quotation asks every supplier of a product the same thing: (1) the quantities are the orders really placed — the smallest, the usual one, the largest (`RfqLineData.tiers`); with one order on file there is no smaller or larger one, and none is made up; (2) a yearly requirement is said only as the company confirmed it, or scaled from the invoices the way the product dataset does and called an indicative estimate — never the sum of a few months passed off as a year; (3) one delivery basis for everyone — DAP the town registered in Settings (`settings.delivery_place`; with none, only the country and "address on request": no address is invented), net of VAT, with FCA as a second figure and duties to state for goods from outside the EU; (4) the questions of the material (`rfqCategoryOf`: a price formula for wax, mould costs for containers, burn tests for wick cord, dies for cardboard, tolerances for metal parts, print set-up for labels) are added when every product of the request is that material; (5) as before, the text never carries the price paid or the current supplier, and nothing is sent by the app.
- Product statuses (`intel/statuses.ts`): Action, Review, To classify, Needs cost data / history / alternative, Ready, Good. A product with a known price and supplier and nothing to compare with is "Ready", not a problem; "Needs alternative" is for products that weigh on the spend (pareto) or have unusable offers on file.
- Products page: priority view by default (top spend, increases, single source, opportunities), the whole list one click away; the search box is parsed by `lib/catalog/query.ts` (supplier names, "over 10k", "single source", words in any form) and says back what it understood.
- Sourcing (`src/lib/sourcing/`, pure, tested; `src/server/sourcing.ts`; pages under `/sourcing`): alternative suppliers and market evidence for the products that make up most of the spend. Rules that must hold: (1) there is no "market price" — a market range exists only from several comparable observations, or one real comparable quote (`market.ts`, `range.reliable`); one published reference is "a benchmark", shown with how far the price is from it and "No reliable market range available" — no position, no amount; (2) every price shows its kind with `PriceTypeTag` (Actual, Quote, Benchmark, Trade data, Cost driver, Public price, Estimated range) and every external fact its source and source level; a price in another currency is compared only with an exchange rate on file (`fx_rate`, from a provider), otherwise shown as written; (3) a gap is a "theoretical opportunity", never a saving; (4) suppliers are never invented and a candidate is not a supplier: `supplier_candidates` rows come from research (kept only with a source URL, `acceptDiscovered`), from a research file, or from the user; they become a `suppliers` row only through `convertCandidate` on the user's click; a candidate's price is a "public price", an offer is recorded as a quote; validating a candidate never validates the product; (5) external data comes only through the provider interfaces in `providers.ts`, with adapters in `src/server/providers/` switched on from the environment (free public sources on by default, web search by API key, premium sources a place with no adapter); a source that is off is said to be off; mock providers live only in tests and are named as mocks; (6) requests for quotation (`rfq.ts`) are drafts to copy or download, never sent, and never mention the price paid or the current supplier; (7) true cost is not computed — say so, never approximate it. Thresholds live in `SOURCING_CONFIG`.
- Deep research (`src/lib/research/`, pure, tested; `src/server/research.ts`): one run per product (`research_runs`, history kept), every finding a `research_evidence` row with its source, page, date and excerpt. The pipeline: classify the product (`strategy.ts` — rules on kind, unit, name and the buyer's own name, no industry logic; the user can override) → queries → web search results reduced to sites (`leads.ts`: marketplaces and directories dropped) → each site's own page read once (`inspect.ts`) — a lead becomes a candidate only if its page states the product; product without the specification is "possible, to confirm", never "exact"; a product name that says nothing is not checked at all → FX for references in other currencies → trade statistics only for products bought by weight with a customs code (suggested from the taxonomy until the user confirms it) → conclusions (`conclusions.ts`, stored messages). A run never writes to purchases, prices or suppliers, never fills in a price, minimum order, lead time or certification the source does not publish, and never overwrites the user's own judgement of a candidate. Every outside call goes through `Sources` in `research.ts`: cached (`research_cache`), counted (`research_usage`), limited (`budget.ts`, limits from the environment). Stored research texts are `say()` messages; free text written by a person (notes of a research file) stays as written.
- From candidates to a request for quotation (`src/lib/sourcing/screening.ts`, `rfq.ts`, `reply.ts`; pure, tested): candidates are screened into a funnel (not suitable, low priority, discovered, plausible, strong) with the reason, technical fit before anything commercial; a published price never lifts a candidate that does not supply the product; nothing is deleted and the user's own judgement overrides the rules. At most `shortlistSize` suppliers are recommended per product, the first round is for the `focusProducts` largest by spend, and research depth follows spend (`limitsFor`). "Recommended" here always means "for a request for quotation" — never recommended to buy from. The same company on several products is one outreach with one multi-line request (`supplierOpportunities`); who was asked and when lives in `rfq_requests`, written only when the user says a request was sent — the app sends nothing, and proposes an update or a follow-up instead of a second request. A supplier's answer is read into quote fields by rules (`readReply`): ambiguous values stay empty with the words found, and the user confirms before a quote is saved (which is also when the candidate becomes a supplier). A partly comparable benchmark never enters a range once a real offer is on file; "lowest nominal quote" needs two comparable offers, and "lowest true cost" stays not available.
- Closing the cycle (`rfq-spec.ts`, `true-cost.ts`, pure, tested): (1) what goes to an alternative supplier is the product's neutral name, specification, application and data sheet (`products.rfq_name`, `technical_specifications`, `application`, `product_documents`) — never the invoice name when it carries the current supplier's name or code; a product that can't be described in neutral words is "not ready" and no request can be prepared for it; "ready" is said only when a person wrote or confirmed the neutral description and the specification (`RfqSpec.confirmed`) — a description, a grade or a size read from the invoice name is a proposal: the request can be prepared ("partial") and says what to confirm; nothing technical is ever filled in by the app. (2) A market range is a range of quotes: none → not available, one → "1 quote received", two or more comparable → range; benchmarks and trade data are shown apart, each with its own gap, and never averaged with quotes (`MarketRange.kind`). (3) True cost is computed from a quote plus inputs kept in `true_cost_scenarios` (inputs only — the result is derived): each component carries its basis, a required component nobody gave makes the result incomplete with no total, an unknown Incoterm is a warning and low confidence; the rates come from Settings or, declared as assumptions, from `SOURCING_CONFIG`. `estimatedTrueCost` of the older comparison engine stays null: true cost lives here. (4) Three words, never mixed: theoretical opportunity (benchmark or nominal prices), opportunity to validate (real quote, complete true cost, something still open), validated opportunity (also the specification confirmed by the user). "Saving" is what an invoice proves and is not computed. "Lowest quote" and "lowest estimated true cost" are stated apart and need two comparable offers. (5) `readReply` settles a number that can be read two ways only when the price paid today makes one reading absurd; several prices that can't be assigned stay empty. (6) The live pilot is the set of products with `products.in_pilot`; until the user chooses, the largest by spend stand in. (7) A benchmark about a month takes that month's average exchange rate (`period_month`, `fx_method`).
- Negotiation intelligence (`src/lib/negotiation/`, pure, tested; `src/server/negotiation.ts`; the card on the product page, one line on the market page, a list on Opportunities): for one product and this buyer, an achievable price range, a suggested target inside it, a confidence and the reasons. Rules that must hold: (1) it is an estimate and says so — never a market price, a quote or a saving; what the target is worth is a "potential negotiation upside", always theoretical: "validated" comes only from a real quote's true cost (`true-cost.ts`), a saving only from an invoice; (2) the range is anchored on price evidence, never on a percentage of the current price: real offers on true cost set both ends (one offer moves the cautious end halfway until a second confirms it), published references are counted for a part of their distance (weights in `NEGOTIATION_CONFIG`) scaled by the buyer's negotiation strength, and the cautious end goes above today's price only by a share of the rise the buyer's own invoices show; a quoted price whose true cost is incomplete counts for half, with a warning; a published reference never overrules a real offer; (3) with no evidence able to stand on its own (the buyer's invoices alone, border averages under a customs code nobody confirmed, system estimates) there is no range: "not enough data", and what to get — nothing is estimated in its place; (4) the buyer's negotiation power is six scores read from what is on file, weighted by the kind of product (`profileOf`: commodity, standard, custom, packaging, other — from the research class and the catalogue kind, never from a company's own categories); they are shown in words, never as figures. The buyer's own leverage is made of the product's volume, the usual order size, whether orders could be grouped or committed, and the supplier relationship leverage (`relationship.ts`): everything bought from the supplier, read from the invoices as five scores (total spend, cross-category spend, breadth, regularity, bundle potential). Spend is never counted twice: cross-category spend is the supplier's total minus this product, and the buyer's power takes from the relationship only what lies beyond the product's own volume. It is leverage, never a discount: more products bought move the power, not a price by themselves, and real offers still set the range. Nothing on file knows the supplier's side, so until the user says how much the company matters to the supplier (`buyer_importance`) the relationship score is capped and its confidence held down; its figure out of ten is shown only in the leverage analysis, next to the facts and thresholds it comes from; (5) every input shows its status (confirmed, estimated, missing), source and method, taken from the product dataset wherever the field lives there; what a person knows better than the rules (switching difficulty, standardization, criticality, the buyer's importance to the supplier) is kept in `product_data_fields` with its reason and the software's own estimate, and wins over the rules; (6) figures are given at three significant figures of the price paid (`precisionOf`) — no false precision; (7) the estimate is always worked out fresh from the evidence: `negotiation_estimates` only keeps what was said each time the visible answer changed (`history.ts`; written once the response is out, after every action and after a product page is shown — `keepEstimateHistory`); (8) every price the engine uses carries a data class (`data-class.ts`): purchase prices, quotes, estimates and targets are private to the account that owns them; only what a supplier publishes itself and aggregate benchmarks are public — `publicView` is all that may ever be shown about a stored estimate outside its account. Nothing here writes a price, a quote or a supplier.
- Supplier entity resolution (`src/lib/suppliers/resolve.ts`, pure, tested; `src/server/suppliers.ts`; the suppliers page and each supplier's page): the same company written in several ways is read as one. Rules that must hold: (1) the hierarchy is VAT number, tax code, web domain, the same normalized name (`companyKey`), a similar name — with phone and city only as support. A name alone never proves anything, and two different VAT numbers are two legal entities whatever their names say; (2) a merge is a pointer (`suppliers.merged_into_id`), never a rewrite: the merged record keeps its name, its purchases and its quotes, every read goes through `canonicalIds` (`readDataset`, `readLearning`, `readSourcing`), and taking a merge back is clearing the pointer. No purchase's supplier is ever changed; (3) records are merged without asking only on a strong identifier (`automatic`: the same VAT number or tax code). A shared web domain is a strong proposal, never a merge by itself — the companies of one group share a site — `autoMergeSuppliers`, run after the writes that may create a supplier. Everything else is a suggestion the user merges or keeps separate; what was decided lives in `supplier_resolutions` (history, undo, the pairs not to propose again), and a merge taken back is never made again by itself; (4) the names a document wrote are never lost: they stay on `import_items`, on the merged records and in `supplier_aliases`, and `supplierIdentity` lists them with how each line was tied to the company; (5) imports match with the same hierarchy (`matchSupplier`): VAT number and tax code first, a name written on a merged record leads to the company it is read as, and the same name with a different VAT number is a question, not a match — the review shows the two numbers, "create a new company" is the first answer, and linking them anyway is refused on the server (`VAT_CONFLICT`) unless the person says so in a second step, recorded as `confirmed_other_vat`; (6) no language model is called: rules decide what is proposed, identifiers what is merged. Code that takes a supplier id from a raw row (a purchase, a candidate, a product's current supplier) resolves it with `canonicalSupplierId` / the `canon` map first. The supplier relationship leverage is read on the canonical supplier.
- Companies and their roles (`src/lib/companies/`, pure, tested; `src/server/companies.ts`; the pages `/companies` and `/companies/<id>`, a link from every supplier, reply and directory page): one `companies` row per legal entity, and the records of today's archives — `suppliers`, `supplier_candidates`, `market_suppliers`, `rfq_suppliers`, the supplier `organizations` — are its roles, each keeping its own data and pointing to it with `company_id`. Rules that must hold: (1) `syncCompanies` gives a company to every record that has none (run after writes by `keepCompaniesInSync`, and before the companies pages are read; idempotent, logged as the app's rules) and never moves a record already tied; (2) records are tied by themselves only on the same VAT number or tax code (either field), or because the app already holds them as one — a supplier record merged into another, a candidate converted into a supplier, a registered company invited as one of the buyer's records, a person's "the same company" on a reply; the candidates of one company for several products are one company (its site, else its name), as they always were read; (3) a shared site or the same name across archives is a proposal (`companyProposals`), never a merge; two different VAT numbers are never "the same company" (`relateCompanies` refuses it); (4) what a person says of two companies lives in `company_relations` with who and when — the same company (a pointer, `companies.merged_into_id`, taken back with `undoCompanyRelation`), of one group, controlled by, distributing, or two different companies (not proposed again); (5) a company's facts are read from its records: an identifier fills a gap and never replaces one; contacts are written by a person (`company_contacts`, deleted only with the whole row logged) or shown from the records with where they come from — never made up; (6) nothing here changes a supplier, a candidate, a directory record, a reply or a purchase. A company listed is not a supplier: its roles say what it is to the buyer. The suppliers list can be read by what they supply (materials, components and packaging, or services and other spend).
- Sourcing strategy (`src/lib/portfolio/`, pure, tested; `src/server/portfolio.ts`; the page `/strategy`): for the products that weigh most (`PORTFOLIO_CONFIG.rounds`), today's mix of suppliers and the mix that would do best on one objective at a time — lowest cost, bundle, specialists, total economic value, quality, delivery, risk, cash flow, fewer suppliers, balanced, custom weights. Rules that must hold: (1) there is no supplier that is right for everything and nothing here chooses one: a mix is something to examine, "evaluate a switch" is the strongest thing said, and nothing is written — the objective, the weights and the limits travel in the page's address (`params.ts`); (2) a product is given only to a supplier with a price for this buyer — the price paid or a real offer (true cost when complete; a quoted price whose true cost is incomplete is theoretical and stays out of "total economic value"). A candidate nobody asked is counted as possible coverage, never allocated and never compared; (3) every mix is read as its advantage over today's, criterion by criterion (`advantages`): what is not on file gives no advantage, so a supplier is never preferred on a lead time, a payment term or a quality nobody wrote down, and an objective whose own data is missing says "not enough data" with what to collect — quality has no record in the database yet and is never scored; (4) coverage is weighed by spend, not by the number of products, and is a bonus next to the cost (weights in `PORTFOLIO_CONFIG`), never a winner by itself; a single-product supplier is judged on its product and is never penalised for covering one; (5) consolidation is leverage and dependence at once: every mix shows its concentration and a risk read from dependence, single sources, suppliers never bought from and distance; a heavy product can be shared between two suppliers (`dualSplit`); (6) an advantage is what the prices on file say, split by what stands behind it (theoretical, to validate, validated — `true-cost.ts`'s words) and never called a saving; the negotiation upside with the suppliers that stay is shown apart and never added to it; what one more supplier costs to manage is valued only when the user says it; (7) limits the user sets (share, number of suppliers, lead time, area, suppliers to leave out, products to keep, two sources for critical products) are respected or said to be impossible on the data on file — never silently dropped. Who could take several products of the same supplier at once also reaches negotiation intelligence (`competition.bundle`): a reason and a small bonus, still "on paper" until a real offer.
- Categories and the product picker (`src/lib/catalog/tree.ts`, `find.ts`, pure, tested; `src/server/categories.ts`; `ProductCategoryPicker` in `src/components/catalog/category-picker.tsx`; the page `/products/categories`): category › subcategory › product is a tree read each time, never stored. Rules that must hold: (1) a product is filed by the names it carries (`products.category`, `products.subcategory`); `product_categories` holds only what the company decided about the hierarchy itself — a name it changed, a subcategory it moved, the order, a category with no product yet. A category that only products name needs no row, and places are addressed by name, never by id; (2) nothing files a product by itself: one with no category is "To classify" until the user, or the Product Mapper confirmed by the user, says what it is. A move made on the categories page is the user's answer and marks the product confirmed; back to "To classify" un-confirms it, so that the mapper proposes again; (3) what is not a product of the catalogue (transport, services, utilities…) sits under one node, "Other spend", by kind, after the categories: never mixed with materials, never moved into a category; (4) renaming or moving rewrites the names on the products and on their families in one go, and keeps the built-in key (`taxonomy_key`), so that what the rules read as "paraffin" is filed where the company put its paraffin (`categoryNaming`: the mapper's proposals, `rfqCategoryOf`, the searches). Code that needs the built-in subcategory of a product asks `subKeyOf`; it never compares labels; (5) a category with products is never deleted, a rename never folds two categories into one, an emptied category stays until the user takes it off, and no purchase, price or invoice is touched; (6) a filter is a set of products at any of the three levels (`resolve` → `productIds`), kept in the page's address (`category`, `subcategory`, `product`: a product alone is enough, its place is read from where it is filed today; an address that names nothing matches nothing, never everything). Filters are independent: choosing a category never touches the supplier or the dates; (7) the picker never grows down the page — eight rows and a scroll of its own (`ROW`, `BODY`) — and on a phone it is a sheet from the bottom, one level at a time; (8) the search (`findProducts`) reads the name, a code, and every way a document wrote the product (`terms`): whole words, then beginnings, then a letter wrong — the last only when nothing is found as typed — and a number is never read with a digit wrong. No language model is called. A page that chooses a product uses this picker (`mode="product"`) rather than a select of every product; `mode="filter"` applies each level as it is clicked.
- Market directories (`src/lib/markets/`, pure, tested; `src/server/markets.ts`; the pages under `/sourcing/directory`; `/export/market/<market>`): the companies of the world that make one kind of thing — the first market is plastic candle containers — found by research, one record per company (`market_suppliers`). Rules that must hold: (1) a company of a directory is not a supplier and not a candidate: nothing here writes to `suppliers`, it becomes a candidate for a product only on the user's click (`makeCandidate`, through `addCandidate`, with the page that shows it), and it is never shown outside the account or sent anything; (2) every record has the exact page that shows it (`evidence_url`); a marketplace listing is a lead, not proof of production (`source_level`); a field its pages do not state is left out and shown and exported as "MISSING" — an email, a size, a material is never made up; (3) the same company is one record (`sameCompany`: its site, else its name), a file that names it again refreshes what its pages say, and a status the user recorded is never taken back by research (`RESEARCH_STATUSES` are the only ones a file may carry); (4) a research is never called complete: each file (`.data/research/markets/`, loaded with a check and a confirmation like any other) carries its coverage — per country: searched in depth, first search only, nothing found, still to search, with the searches made — its gaps and the names met and not verified (`leads`, which are not suppliers); (5) a container sold for candles is not for that reason safe: the intended use (made for hot wax, for a finished candle, sold empty, an outer support) is recorded only when documented, otherwise "technical validation required", and a material certificate never stands for a test on the finished candle; (6) a directory belongs to no company: which of the buyer's products a market serves is read from where they are filed (`MarketDefinition.serves`, through `subKeyOf`), and what the buyer's records say of a company (a supplier already, a candidate, asked, answered) is derived each time (`readLinks`), never stored on the record; (7) filters are independent, offer only what is on file, and the countries offered are those of the continent chosen. A new market is one more entry in `MARKETS`.
- Replies to requests for quotation (`src/lib/replies/`, pure, tested; `src/server/replies.ts`; the pages under `/sourcing/replies`): the companies that answered a request, what each said and the prices it stated — kept as written. Rules that must hold: (1) a company that answered is not a supplier and not a candidate: it is an `rfq_suppliers` row with its conversations (`rfq_threads`, one per request: its own status, what is missing, the next action), the lines it quoted (`rfq_offers`) and the messages all this was read from (`rfq_messages`). Nothing here writes to `suppliers`, `supplier_candidates`, `quotes` or a market directory; what those records say of the same company is derived each time (`elsewhereOf`; `readLinks` for a directory) and only pointed out; (2) an offer is the company's own product at its own price: currency, unit, quantity, delivery terms and destination are kept as stated. It is tied to none of the buyer's products, enters no comparison, range, average or ranking, and is never converted to another currency or to a delivered price (`deliveryOf` says in words what a price includes). How far it is the product bought is its technical compatibility, which only a person moves (below): a file never validates; (3) five statuses (`REPLY_STATUSES`), read from the source's own words (`readStatus`: a refusal first) and kept next to them; a status nobody can read sets the record aside, it is not guessed. A price received whose product nobody verified shows both statuses (`statusesOf`); (4) a file is checked before it is loaded, by the same plan (`planReplies`): new companies, companies on file and what would change, offers to add, records set aside with the reason. The load is one transaction, and loading a file twice changes nothing (the request reference, the offer line and the message are keys); (5) the same company is never written twice: the same request reference, a VAT number, a tax code, its own domain with a name that agrees or with its phone number, or the same name (`sameCompanyAs`, on `compareSuppliers`); a resemblance is said and decides nothing; (6) a value on file is never emptied by a file that leaves it out, never replaced by an older file, and never replaced once a person wrote it (`confirmed`): the difference is listed. What a person says about a conversation goes in its history (`updateReplyThread`); (7) every record is kept whole as the source gave it (`original`), also when its reading had to put its fields back in place; (8) the files (`.data/research/replies/`, or chosen by hand) are the buyer's private data: tests use the mock in `fixtures.ts`, never a real file. Nothing is sent, and no badge is given.
- Offers and the buyer's products (`src/lib/replies/match.ts`, `offers.ts`, `landed.ts`, `rows.ts`, pure, tested; `src/server/replies.ts`, `audit.ts`, `destinations.ts`; the section "Quotes and alternatives" on the product page, the offer's page `/sourcing/replies/offers/<id>`): what the replies mean for a product. Rules that must hold: (1) three things are kept apart — where the conversation stands (commercial), how far the offer is the product bought (`COMPATIBILITIES`: not analysed, possibly compatible, awaiting specifications, sample to test, equivalence validated, not equivalent — always with its reason), and whether its cost is known to the plant. A link between an offer and a product (`rfq_offers.product_id`) is not an equivalence: a link is never made as "validated", and equivalence can be said only of a linked offer; (2) the app proposes, a person confirms: `suggestFor` proposes a product for an offer only when both are the same kind of thing (the catalogue's subcategory, read from the offer's words) in the same unit — "pz" and "pcs" are one unit written two ways — or in a unit that converts exactly (`unitsPer`: a tonne holds 1000 kg, "1.000 pz" holds 1000 pieces; boxes, rolls and pallets never convert): proposed, its price kept as written; when both carry a grade written as a range it says how they stand, and a grade that does not overlap is proposed as "not equivalent" — another grade, never the same product. Proposals are derived each time and stored only on the user's click; "not for this product" is remembered (`declined_product_ids`). Similar names decide nothing; (3) an offer's state (`offerState`: price received, technical review, commercial review, awaiting the supplier, validated, not comparable, expired, superseded, rejected) is derived, never stored — only a person's refusal is. A line quoted again is a new row: the earlier one is `superseded` and stays as history; an expired offer stays on file and is never an active one; (4) an offer is comparable (`groupOf`) only when it is linked, technically validated, valid on a stated date that has not passed, in the product's unit or one that converts into it exactly (`unitFactorOf`), with a complete landed cost. Only then is it set against the price paid — per the product's unit (`OfferView.perProductUnit`; quantities and minimum orders converted the same way), the price as quoted staying on the offer (`savingOf`: a "potential saving" on the volume really bought, with the limit said when the minimum order exceeds a year's volume). Everything else is "to verify" with what is short (`shortfallsOf`); other grades are shown apart and never ranked; (5) true landed cost (`landedCost`): the delivery terms say what the price includes, and nothing included is added again whatever was typed; every figure a person states carries confirmed/estimated, source and date; a figure nobody gave is missing and the cost then has no total — no freight, duty or exchange rate is made up, a price in another currency is converted only at a stated, dated rate, and VAT is left out; (6) documents (`rfq_documents`): named, linked or uploaded — only an upload is a copy on file, and the page says which (`availabilityOf`); (7) one company in several parts of the app is tied by what identifies it; what only resembles is a proposal a person settles — the same company, the same group, or two companies (`company_links`: a pointer, never a merge; it can be taken back); (8) who did what (`audit_events`): every write of these modules logs actor, action, record, old and new value in the same transaction. A file's doing is `import`, the rules' is `system`, a person's is `user`, an assistant's is `ai`: an assistant that operates the app sets the cookie `pi_actor=assistant` in its own browser before it touches anything and clears it afterwards, so that nothing it does is recorded as the person's. A wrong attribution is corrected only with evidence (`correctAttribution`), and what it said before is kept; events older than the log are `reconstructed` or `uncertain`, never invented; (9) delivery destinations (`delivery_destinations`, in Settings) are written and confirmed by a person; changing a confirmed address un-confirms it; none is ever taken from an offer. The default one is what requests name and what a landed cost is worked out to; (10) a quoted price is the buyer's private data (`OFFER_DATA_CLASS`): never shown as a supplier's list price, never in a public page. Who may read what is said below (companies, people, the two areas).
- From the replies to the analysis (`src/lib/replies/bridge.ts`, pure, tested; `readComparableOffers` in `src/server/replies.ts`; read by `getIntel` and `readMarketViews`): an offer that passed every check — tied to a product, technically validated by a person, within its date, in the product's unit, with a complete landed cost (`groupOf` = comparable) — is read by Compare, the market view, negotiation and the sourcing strategy as a quote. Rules that must hold: (1) it is read, never copied: no row is written to `quotes` or `suppliers`, and the offer stays the one source — the instant it expires, is superseded, is untied or loses its validation it is a quote for nobody, everywhere; (2) only comparable offers cross: anything short of that stays on the product's page among the offers to verify and enters no comparison, range or ranking; (3) what crosses is the cost to the plant in euro (`QuoteData.landed`, `validated`): nothing is added to it again, and it is not flagged as "import costs not assessed" or "specifications not compared" — the price as the company quoted it stays on the offer; (4) the company is carried into the analysis as itself (`reply:<id>`), never listed among the suppliers, and its page is its reply card; when it is a supplier on file — by what identifies it, or because a person said so — the quote is read under that supplier; (5) never make the real offers comparable to see the bridge work: tests use the mock.
- Offers still to verify (`src/lib/replies/pending.ts`, pure, tested; `readPendingOffers` in `src/server/replies.ts`; `Intel.pending`, read by `getIntel`): the active offers received for a product that are not comparable yet, with what each lacks. They are named wherever a buyer looks — the decision engine's status, next action (`verify_offers`: "Verify the n offers received", never "get a quote" while offers wait) and plain-language summary, the executive summary, the recent changes, Compare and the market page (`PendingOffersSection`), the supplier's observations, the bell (an offer ending today by name, those ending within `EXPIRING_DAYS`, the replies that came lately) — and they enter no figure: no saving, no range, no ranking, no market reference. The price is shown as quoted, with its quantity; one offer proposed for several products is counted once. Words for them are worked out in `decision.ts` / `pending.ts`, never in a component.
- What is asked of a company about an offer (`requestFromSupplier`) — more information to judge it, or a price still valid — is written on the offer (tied to the product as "awaiting specifications", with what is needed as the reason) and on its conversation (what is missing, the next action, when to come back). Nothing is sent. Associating an offer with a product is never an equivalence: the association and the technical compatibility are shown apart, and an equivalence is said only by a person, with the reason. A resemblance between two company records can be put off (`later`): it stays an open question. A document is "on file" only as an uploaded copy; a name or a link is "not acquired yet" and cannot be marked as checked.
- Exchange rates (`src/server/fx.ts`): a rate comes from a provider of official reference rates (the ECB adapter) or from a person with its source and date — never made up; it is offered as an estimate, kept where it was used with its date, and only ever used to read a price next to prices in euro: the price as quoted is never replaced.
- Companies, people and the two areas (`src/lib/auth/cookie.ts`, `src/server/auth.ts`, `orgs.ts`, `session.ts`, `src/proxy.ts`): one installation is one buyer's workspace — everything under `src/app/(workspace)` — and a supplier portal under `src/app/(outside)/portal`, with its own frame that reads nothing of the workspace. - Direct Order (`src/lib/orders/`, pure, tested; `src/server/order-catalog.ts`, `orders.ts`; the buyer's pages `/orders`, the sections on product, supplier and reply pages; the portal): a private channel for orders between the buyer and a supplier that registered, switched on in Settings (`settings.direct_order`; off, none of it answers and the portal does not exist). Rules that must hold: (1) "Order Ready" is never stored and never granted: it is worked out each time (`listingState`) from the supplier's company data given once (`orgGaps`), an article precise enough that nobody could take it for another — its code, a name and technical description, the supplier's confirmation (`identityGaps`) — the six conditions complete and confirmed by an authorised person (`missingTerms`: price, minimum and step, lead time, delivery terms, payment terms, validity), and a price still within its date: past it the article stops by itself. It is not a badge of reliability and cannot be bought; (2) conditions are stated by the supplier and nothing fills them in: what it already wrote to a customer — its quotation, its invoice — is proposed to be checked, for that customer only (`termsProposals`); one customer's price is never proposed as everyone's, and nothing is switched on from a document; (3) conditions reserved to a customer are read by that customer alone (`readListings` never loads another's); a change of conditions is a new row and the one before is kept; (4) a request is not an order and an order is not a purchase: it is confirmed only when the supplier accepts it as written or the customer accepts the supplier's changes — a proposal is never an order, and another article in place of the one asked needs the customer's approval of the specification in so many words; (5) every change of status is a transition of `flow.ts`, checked on the server against the order as it is at that instant (status and version): nothing is confirmed twice, and the same request sent twice is one order (`idempotency_key`); (6) a confirmed order is written once (`orders.confirmed`) and never rewritten — not by a new price list, not by this code, and the database refuses too (triggers in migration 0022); events are only ever added, each with its author; (7) a total is shown only when it can be worked out (`orderAmounts`): "DAP" alone never means delivered anywhere at that price — when the conditions do not cover the destination there is no total and the supplier confirms or states the transport; (8) a notification names the order and the other company, never a price or a quantity, and is read only by the company it is for; (9) nothing here writes a purchase, a quotation, a supplier or a product, no payment exists, and nothing is sent outside the app. The conditions of the order service (`conditions.ts`) are a pilot draft not reviewed by a lawyer, and say so.

Sourcing readiness is `rfq-spec.ts`'s verdict; true cost readiness is judged apart and never blocks sourcing. The priority list and its order are the existing Pareto; the first round is `DATASET_CONFIG.topProducts`. The CSV export (`/export/product-dataset`) is a copy: the database stays the source of truth.
