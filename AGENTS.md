# Project notes

Procurement Intelligence prototype for manufacturing SMEs. See README.md (Italian) for setup and architecture.

- All business numbers are computed in `src/lib/analytics.ts` (pure functions, tested). Never store derived values (current price, price history, spend) in the database.
- All writes go through `src/app/actions.ts` (or an importer with preview → approval). Validation schemas live in `src/lib/validation.ts`.
- Schema changes: edit `src/db/schema.ts`, then `npm run db:generate`; migrations in `drizzle/` apply on startup.
- Two languages, English and Italian (`src/lib/i18n/`). The English text written in the code is the key; its Italian lives in `src/lib/i18n/it/*.ts`, and a text missing there does not compile (`Msg`). Never put user-facing text in the UI or in an engine without going through the translator: `await getT()` in server components, route handlers and actions (`lib/data.ts`), `useT()` in client components (`i18n/client.tsx`), a `t: T = en` argument in pure functions (English default, which is what the tests read). Label tables are typed `Msg` and translated where shown. Whole sentences, not fragments: `t("{n} lines ready", { n })`, `t.n(count, one, many)` for plurals, `rich()` when an element sits inside a sentence, `"Open|status"` when one English word has two meanings. The language is a setting (`settings.language`), changed from the top bar or Settings.
- Messages stored in the database (import issues, match reasons, file errors) are saved in English with their template and values (`say()`) and shown with `said(t, …)` / `t.any(…)`, so they follow the reader's language later.
- Numbers and dates use Italian formatting in both languages via `src/lib/format.ts`; month names and words like "days" go through the translator. Countries are compared with `countryKey()` and shown with `countryName()` (`lib/countries.ts`): "Italy" and "Italia" are the same place.
- Compare/alternatives must never rank or call a supplier "cheaper" until landed cost exists.
- Verify with `npm test`, `npm run typecheck`, `npm run lint`.
- Imports never write facts directly: file → import_items → user review/approval (`src/server/imports.ts`). Unit/currency/number/date parsing lives only in `src/lib/import/normalize/`; never guess an ambiguous value — flag it for review.
- Import scenarios: `test-data/` (regenerate with `npx tsx scripts/make-test-data.ts`); end-to-end tests in `src/server/imports.test.ts` run on in-memory PGlite.
- Price intelligence lives in `src/lib/intel/` (pure, tested): thresholds only in `config.ts`, explanations in `explain.ts`. Demo data is a test fixture — never shape logic around it; add generic cases to `src/lib/intel/fixtures.ts` tests instead.
- Savings vocabulary is strict: "price difference" (nominal) vs "potential saving" (estimate, price only) — never "saving realised", never "best supplier". No saving for non-comparable offers.
- Opportunities are computed by the engine; the `opportunities` table stores only the user's status/note/snapshot.
- The home page (`/`), the full review (`/report`), the product page and Compare all render `src/lib/intel/decision.ts` (summary engine: status, alternatives, next actions, plain-language text, priority). It selects and words what `analyze()` computed — no new price/saving formulas there, and no status or sentence worked out inside a React component.
- Landed cost, external benchmarks and supplier quality data do not exist yet: never show them as numbers (`estimatedTrueCost` stays null, market reference is `internal_quotes` or `not_available`).
- UX rules (keep them): simple first, detail on demand. One global "+ Add" and one entry panel (`src/components/entry/`) — pages open it through `useEntry()` / the `*Dialog` buttons, never with their own form or option lists. Forms ask only what can't be inferred; optional fields go under `MoreDetails`. Secondary sections use `Disclosure`. One product status everywhere (`DecisionStatusPill`). Table columns are shown by container width (`@2xl:table-cell`…), not viewport. No jargon in labels (MOQ → "minimum order"); the technical term goes in a `Hint`. Never label a supplier best/winner/recommended to buy from ("recommended for a request for quotation" is the only recommendation the app makes).
- Imports: `createUpload(..., "auto", { autoMap: true })` from the UI; the service default stays explicit. Column guesses from values (header-less paste) are never applied without the user checking them.
- Not everything on an invoice is a product. `products.kind` (`src/lib/catalog/kinds.ts`) says what each item is: materials, components and packaging are the catalogue Procurement Intelligence works on (`getIntel()` runs on `catalogueOf(data)`); transport, services, utilities and the rest are company spend (`getSpend()`), one item per supplier and kind, never compared or watched for price changes. Supplier spend counts everything.
- Unknown products of an import are never asked one by one or created as written: `src/lib/catalog/propose.ts` groups them (pure, tested) and `src/server/catalog.ts` creates products only on the user's confirmation. Names alone never merge two products; a different number in the name keeps them apart unless the supplier's own code says otherwise, and then the user is asked. Classification is rule-based (`classify.ts`): add a word to the list of its kind; what the rules can't tell stays "to classify" and is asked — never guessed.
- Product Mapper (`src/lib/catalog/mapper.ts`, pure, tested; `src/server/mapper.ts` writes): reads the catalogue's products and proposes a readable name, category › subcategory (`taxonomy.ts`: add a word to its subcategory), family and variant, with a level — high (the name says it: bulk confirmation), medium (read from the supplier's context, or the name was shortened: shown to the user), low (asked). Possible duplicates are proposed, never merged by themselves; a different size is never a duplicate, a packing note ("60 pz. x scat") is not a size. It is a rule engine: no language model is called. Nothing is stored until the user confirms (`products.mapped_at`); categories, families and names are text the user can rewrite. A mapping never touches prices, quantities, suppliers or dates — a merge only moves purchases under the product that stays.
- Product statuses (`intel/statuses.ts`): Action, Review, To classify, Needs cost data / history / alternative, Ready, Good. A product with a known price and supplier and nothing to compare with is "Ready", not a problem; "Needs alternative" is for products that weigh on the spend (pareto) or have unusable offers on file.
- Products page: priority view by default (top spend, increases, single source, opportunities), the whole list one click away; the search box is parsed by `lib/catalog/query.ts` (supplier names, "over 10k", "single source", words in any form) and says back what it understood.
- Sourcing (`src/lib/sourcing/`, pure, tested; `src/server/sourcing.ts`; pages under `/sourcing`): alternative suppliers and market evidence for the products that make up most of the spend. Rules that must hold: (1) there is no "market price" — a market range exists only from several comparable observations, or one real comparable quote (`market.ts`, `range.reliable`); one published reference is "a benchmark", shown with how far the price is from it and "No reliable market range available" — no position, no amount; (2) every price shows its kind with `PriceTypeTag` (Actual, Quote, Benchmark, Trade data, Cost driver, Public price, Estimated range) and every external fact its source and source level; a price in another currency is compared only with an exchange rate on file (`fx_rate`, from a provider), otherwise shown as written; (3) a gap is a "theoretical opportunity", never a saving; (4) suppliers are never invented and a candidate is not a supplier: `supplier_candidates` rows come from research (kept only with a source URL, `acceptDiscovered`), from a research file, or from the user; they become a `suppliers` row only through `convertCandidate` on the user's click; a candidate's price is a "public price", an offer is recorded as a quote; validating a candidate never validates the product; (5) external data comes only through the provider interfaces in `providers.ts`, with adapters in `src/server/providers/` switched on from the environment (free public sources on by default, web search by API key, premium sources a place with no adapter); a source that is off is said to be off; mock providers live only in tests and are named as mocks; (6) requests for quotation (`rfq.ts`) are drafts to copy or download, never sent, and never mention the price paid or the current supplier; (7) true cost is not computed — say so, never approximate it. Thresholds live in `SOURCING_CONFIG`.
- Deep research (`src/lib/research/`, pure, tested; `src/server/research.ts`): one run per product (`research_runs`, history kept), every finding a `research_evidence` row with its source, page, date and excerpt. The pipeline: classify the product (`strategy.ts` — rules on kind, unit, name and the buyer's own name, no industry logic; the user can override) → queries → web search results reduced to sites (`leads.ts`: marketplaces and directories dropped) → each site's own page read once (`inspect.ts`) — a lead becomes a candidate only if its page states the product; product without the specification is "possible, to confirm", never "exact"; a product name that says nothing is not checked at all → FX for references in other currencies → trade statistics only for products bought by weight with a customs code (suggested from the taxonomy until the user confirms it) → conclusions (`conclusions.ts`, stored messages). A run never writes to purchases, prices or suppliers, never fills in a price, minimum order, lead time or certification the source does not publish, and never overwrites the user's own judgement of a candidate. Every outside call goes through `Sources` in `research.ts`: cached (`research_cache`), counted (`research_usage`), limited (`budget.ts`, limits from the environment). Stored research texts are `say()` messages; free text written by a person (notes of a research file) stays as written.
- From candidates to a request for quotation (`src/lib/sourcing/screening.ts`, `rfq.ts`, `reply.ts`; pure, tested): candidates are screened into a funnel (not suitable, low priority, discovered, plausible, strong) with the reason, technical fit before anything commercial; a published price never lifts a candidate that does not supply the product; nothing is deleted and the user's own judgement overrides the rules. At most `shortlistSize` suppliers are recommended per product, the first round is for the `focusProducts` largest by spend, and research depth follows spend (`limitsFor`). "Recommended" here always means "for a request for quotation" — never recommended to buy from. The same company on several products is one outreach with one multi-line request (`supplierOpportunities`); who was asked and when lives in `rfq_requests`, written only when the user says a request was sent — the app sends nothing, and proposes an update or a follow-up instead of a second request. A supplier's answer is read into quote fields by rules (`readReply`): ambiguous values stay empty with the words found, and the user confirms before a quote is saved (which is also when the candidate becomes a supplier). A partly comparable benchmark never enters a range once a real offer is on file; "lowest nominal quote" needs two comparable offers, and "lowest true cost" stays not available.
- New migrations are applied by the running dev server (`getDb()` re-checks the journal): back up `.data` before generating one on a machine with real data.
- Every description found on a document is kept as an alias (`product_aliases`: as written, per supplier, with supplier code, EAN, confidence, confirmation and source import) through `saveAlias()`; aliases of spend items are only recognised for their own supplier.
- Lines that are not purchases (credit notes, zero amounts) carry an issue with `excludes: true` and are set aside (`skipped`) by `evaluateItems`, with the reason; bringing one back acknowledges it. Line identity for duplicates includes the invoice line number when the file has one.
- Electronic invoices (FatturaPA XML, also signed `.p7m`) are read field by field in `src/lib/import/extract/einvoice.ts` / `p7m.ts`: nothing is interpreted, and the signature is not verified.
- Zip files are opened in the browser (`src/lib/import/archive.ts`) and each file inside goes through `createUpload` like a file dropped on its own; the server never receives a zip. What can't be read (unknown type, password, damage, over 20 MB) is listed to the user with the reason, never skipped silently. The accepted extensions and the size limit live in `src/lib/import/files.ts`, shared by browser and server.
- Company settings (`settings` table, one row: name, country, VAT number, user name) are read with `getSettings()`; they are not purchasing data and survive "Clear all data". `src/lib/config.ts` only holds the defaults.
- Visual identity: dark navigation rail (`night` tokens), `ledger` blue for primary actions, colour only for meaning. A percentage or score shown to the user must be a real, explainable ratio (the "Data status" ring is products-with-a-comparison ÷ products).
