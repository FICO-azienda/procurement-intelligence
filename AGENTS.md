# Project notes

Procurement Intelligence prototype for manufacturing SMEs. See README.md (Italian) for setup and architecture.

- All business numbers are computed in `src/lib/analytics.ts` (pure functions, tested). Never store derived values (current price, price history, spend) in the database.
- All writes go through `src/app/actions.ts` (or an importer with preview → approval). Validation schemas live in `src/lib/validation.ts`.
- Schema changes: edit `src/db/schema.ts`, then `npm run db:generate`; migrations in `drizzle/` apply on startup.
- Two languages, English and Italian (`src/lib/i18n/`). The English text written in the code is the key; its Italian lives in `src/lib/i18n/it/*.ts`, and a text missing there does not compile (`Msg`). Never put user-facing text in the UI or in an engine without going through the translator: `await getT()` in server components, route handlers and actions (`lib/data.ts`), `useT()` in client components (`i18n/client.tsx`), a `t: T = en` argument in pure functions (English default, which is what the tests read). Label tables are typed `Msg` and translated where shown. Whole sentences, not fragments: `t("{n} lines ready", { n })`, `t.n(count, one, many)` for plurals, `rich()` when an element sits inside a sentence, `"Open|status"` when one English word has two meanings. The language is a setting (`settings.language`), changed from the top bar or Settings.
- Messages stored in the database (import issues, match reasons, file errors) are saved in English with their template and values (`say()`) and shown with `said(t, …)` / `t.any(…)`, so they follow the reader's language later.
- Numbers and dates use Italian formatting in both languages via `src/lib/format.ts`; month names and words like "days" go through the translator. Countries are compared with `countryKey()` and shown with `countryName()` (`lib/countries.ts`): "Italy" and "Italia" are the same place.
- Compare/alternatives must never rank or call a supplier "cheaper" until landed cost exists.
- Verify with `npm test`, `npm run typecheck`, `npm run lint`.
- Imports never write facts directly: file → import_items → user review/approval (`src/server/imports.ts`). Unit/currency/number/date parsing lives only in `src/lib/import/normalize/`; never guess an ambiguous value — flag it for review.
- Import scenarios: `test-data/` (regenerate with `npx tsx scripts/make-test-data.ts`); end-to-end tests in `src/server/imports.test.ts` run on in-memory PGlite.
- Price intelligence lives in `src/lib/intel/` (pure, tested): thresholds only in `config.ts`, explanations in `explain.ts`. Demo data is a test fixture — never shape logic around it; add generic cases to `src/lib/intel/fixtures.ts` tests instead.
- Savings vocabulary is strict: "price difference" (nominal) vs "potential saving" (estimate, price only) — never "saving realised", never "best supplier". No saving for non-comparable offers.
- Opportunities are computed by the engine; the `opportunities` table stores only the user's status/note/snapshot.
- The home page (`/`), the full review (`/report`), the product page and Compare all render `src/lib/intel/decision.ts` (summary engine: status, alternatives, next actions, plain-language text, priority). It selects and words what `analyze()` computed — no new price/saving formulas there, and no status or sentence worked out inside a React component.
- Supplier quality data does not exist yet. In the decision engine (`decision.ts`) `estimatedTrueCost` stays null and the market reference is `internal_quotes` or `not_available`: true cost and external evidence live in the sourcing module, with their own rules (below).
- UX rules (keep them): simple first, detail on demand. One global "+ Add" and one entry panel (`src/components/entry/`) — pages open it through `useEntry()` / the `*Dialog` buttons, never with their own form or option lists. Forms ask only what can't be inferred; optional fields go under `MoreDetails`. Secondary sections use `Disclosure`. One product status everywhere (`DecisionStatusPill`). Table columns are shown by container width (`@2xl:table-cell`…), not viewport. No jargon in labels (MOQ → "minimum order"); the technical term goes in a `Hint`. Never label a supplier best/winner/recommended to buy from ("recommended for a request for quotation" is the only recommendation the app makes).
- Imports: `createUpload(..., "auto", { autoMap: true })` from the UI; the service default stays explicit. Column guesses from values (header-less paste) are never applied without the user checking them.
- Not everything on an invoice is a product. `products.kind` (`src/lib/catalog/kinds.ts`) says what each item is: materials, components and packaging are the catalogue Procurement Intelligence works on (`getIntel()` runs on `catalogueOf(data)`); transport, services, utilities and the rest are company spend (`getSpend()`), one item per supplier and kind, never compared or watched for price changes. Supplier spend counts everything.
- Unknown products of an import are never asked one by one or created as written: `src/lib/catalog/propose.ts` groups them (pure, tested) and `src/server/catalog.ts` creates products only on the user's confirmation. Names alone never merge two products; a different number in the name keeps them apart unless the supplier's own code says otherwise, and then the user is asked. Classification is rule-based (`classify.ts`): add a word to the list of its kind; what the rules can't tell stays "to classify" and is asked — never guessed.
- Product Mapper (`src/lib/catalog/mapper.ts`, pure, tested; `src/server/mapper.ts` writes): reads the catalogue's products and proposes a readable name, category › subcategory (`taxonomy.ts`: add a word to its subcategory), family and variant, with a level — high (the name says it: bulk confirmation), medium (read from the supplier's context, or the name was shortened: shown to the user), low (asked). Possible duplicates are proposed, never merged by themselves; a different size is never a duplicate, a packing note ("60 pz. x scat") is not a size. It is a rule engine: no language model is called. Nothing is stored until the user confirms (`products.mapped_at`); categories, families and names are text the user can rewrite. A mapping never touches prices, quantities, suppliers or dates — a merge only moves purchases under the product that stays, and can be taken back. The page is "Product cleanup" (`/products/review`): how each product was read (original description, supplier, product, family, supplier's codes, confidence and why), the largest first.
- Product identity (`src/lib/catalog/identity.ts`, pure, tested; read by the mapper, the import matcher and the searches): who sold it is not what was bought, and what the supplier calls it is not what the product is. The description on an invoice is raw source data, kept as written (`product_aliases`, every purchase) and read apart each time — nothing of the reading is stored. Rules that must hold: (1) a word of the seller's own company name is the seller, not the product ("Paraffina SER 52/54" → "Paraffina 52/54"), unless it is also a word for a product, a material or a colour, and unless nothing but a model code would be left (a brand and its model stay as written); (2) the seller's codes are a short code in brackets, a bare number of five digits or more, the article code the document gives, and what stands in front of the noun after "ART." — they are listed as the supplier's codes and left out of the name whenever something else tells the product apart; grades, sizes and weights are the specification and are never touched; (3) every catalogue product has an identity: `named` (the words and the grade say what it is — the only ones confirmed in bulk), `supplier_code` (the words say the kind of thing and only the supplier's article code tells it apart: the code stays in the name, the group is "needs review" and one answer covers a supplier's range), `unidentified` (the words name a material that can be several things — a taxonomy subcategory with `ask` — and nothing says which: it keeps the name it has, gets no subcategory, and the user is offered at most three options, "something else" and "I don't know yet"; no name is ever made up from a code); (4) similar is not the same: two descriptions are the same product only when they name the same thing in the same grade (`compareIdentity`: same, likely, other_spec, unrelated) — another grade is another product of the same family and is never proposed as a match or a duplicate; (5) on import (`matchProduct`) the seller's own code read before on one of its descriptions is recognised when written again; the same identity from another supplier is a "probable" match the user links or keeps apart, never linked by itself; (6) a merge deletes nothing (`mergeProducts`): the rows that can follow (purchases, quotes, import lines, descriptions, candidates, benchmarks, research, documents) move under the product that stays and are logged in `product_merges`, the merged product stays on file with `merged_into_id` and is no longer listed (`readDataset`), and `undoProductMerge` puts everything back; (7) it is better to show "needs review" than to file a product wrong: nothing here optimises for having every product classified. No language model is called.
- Macro product and variants (`src/lib/catalog/macro.ts`, pure, tested; `confirmVariants` in `src/server/mapper.ts`; the cards "One product, several versions?" on `/products/review`): the structure is category › product family (the subcategory) › macro product (the row in `product_families`) › variant (`products.variant`) › supplier's product › description on the invoice. Fewer, cleaner products — never two different articles folded into one to tidy the catalogue. Rules that must hold: (1) articles are proposed as versions of one product only on evidence read together: the same supplier, the same unit, the same product family, names that begin (and may end) the same way with at most `maxVariantWords` words changing in between, and prices that sit together; a matching price supports it and never decides it — two names that do not begin alike are never tied by a price, and a price far from the others' (`priceBand`) leaves the article out, said in the card; (2) what changes is named only as far as the words say: a colour, a size or a capacity written in full is sure; an abbreviation (TR, BIA) is read as a colour only next to one written in full, on this article or on others of the same supplier, and said to be a reading; an ending nothing explains is shown as it is; (3) nothing is grouped by itself: every group has three answers — "they are variants" (the products stay apart, each with its purchases and price, filed under one macro product; what changes is asked and kept in `product_families.variant_by`), "merge" (one product written several ways: `mergeProducts`, which can be undone) and "keep separate" (not proposed again); a family the mapper already proposes is a macro product already and is not asked about twice, and a new version of a confirmed macro product is proposed next to the ones filed; (4) the same product written in another way is a possible duplicate, not a new product: the order of the words, a unit left out and a word cut short ("CONT LC TR 30" / "LC TR CONTENITORE 30 CL") — with the numbers in the same order, since "20x500 30 pz" is not "30x500 20 pz", and every letter counting, since "C5" is not "C5A". Names are split into words by `nameTokens` ("60L" = "60 L", "LC 1" = "LC1", "A B V" one code). Thresholds live in `MACRO_CONFIG`. No language model is called.
- Product statuses (`intel/statuses.ts`): Action, Review, To classify, Needs cost data / history / alternative, Ready, Good. A product with a known price and supplier and nothing to compare with is "Ready", not a problem; "Needs alternative" is for products that weigh on the spend (pareto) or have unusable offers on file.
- Products page: priority view by default (top spend, increases, single source, opportunities), the whole list one click away; the search box is parsed by `lib/catalog/query.ts` (supplier names, "over 10k", "single source", words in any form) and says back what it understood.
- Sourcing (`src/lib/sourcing/`, pure, tested; `src/server/sourcing.ts`; pages under `/sourcing`): alternative suppliers and market evidence for the products that make up most of the spend. Rules that must hold: (1) there is no "market price" — a market range exists only from several comparable observations, or one real comparable quote (`market.ts`, `range.reliable`); one published reference is "a benchmark", shown with how far the price is from it and "No reliable market range available" — no position, no amount; (2) every price shows its kind with `PriceTypeTag` (Actual, Quote, Benchmark, Trade data, Cost driver, Public price, Estimated range) and every external fact its source and source level; a price in another currency is compared only with an exchange rate on file (`fx_rate`, from a provider), otherwise shown as written; (3) a gap is a "theoretical opportunity", never a saving; (4) suppliers are never invented and a candidate is not a supplier: `supplier_candidates` rows come from research (kept only with a source URL, `acceptDiscovered`), from a research file, or from the user; they become a `suppliers` row only through `convertCandidate` on the user's click; a candidate's price is a "public price", an offer is recorded as a quote; validating a candidate never validates the product; (5) external data comes only through the provider interfaces in `providers.ts`, with adapters in `src/server/providers/` switched on from the environment (free public sources on by default, web search by API key, premium sources a place with no adapter); a source that is off is said to be off; mock providers live only in tests and are named as mocks; (6) requests for quotation (`rfq.ts`) are drafts to copy or download, never sent, and never mention the price paid or the current supplier; (7) true cost is not computed — say so, never approximate it. Thresholds live in `SOURCING_CONFIG`.
- Deep research (`src/lib/research/`, pure, tested; `src/server/research.ts`): one run per product (`research_runs`, history kept), every finding a `research_evidence` row with its source, page, date and excerpt. The pipeline: classify the product (`strategy.ts` — rules on kind, unit, name and the buyer's own name, no industry logic; the user can override) → queries → web search results reduced to sites (`leads.ts`: marketplaces and directories dropped) → each site's own page read once (`inspect.ts`) — a lead becomes a candidate only if its page states the product; product without the specification is "possible, to confirm", never "exact"; a product name that says nothing is not checked at all → FX for references in other currencies → trade statistics only for products bought by weight with a customs code (suggested from the taxonomy until the user confirms it) → conclusions (`conclusions.ts`, stored messages). A run never writes to purchases, prices or suppliers, never fills in a price, minimum order, lead time or certification the source does not publish, and never overwrites the user's own judgement of a candidate. Every outside call goes through `Sources` in `research.ts`: cached (`research_cache`), counted (`research_usage`), limited (`budget.ts`, limits from the environment). Stored research texts are `say()` messages; free text written by a person (notes of a research file) stays as written.
- From candidates to a request for quotation (`src/lib/sourcing/screening.ts`, `rfq.ts`, `reply.ts`; pure, tested): candidates are screened into a funnel (not suitable, low priority, discovered, plausible, strong) with the reason, technical fit before anything commercial; a published price never lifts a candidate that does not supply the product; nothing is deleted and the user's own judgement overrides the rules. At most `shortlistSize` suppliers are recommended per product, the first round is for the `focusProducts` largest by spend, and research depth follows spend (`limitsFor`). "Recommended" here always means "for a request for quotation" — never recommended to buy from. The same company on several products is one outreach with one multi-line request (`supplierOpportunities`); who was asked and when lives in `rfq_requests`, written only when the user says a request was sent — the app sends nothing, and proposes an update or a follow-up instead of a second request. A supplier's answer is read into quote fields by rules (`readReply`): ambiguous values stay empty with the words found, and the user confirms before a quote is saved (which is also when the candidate becomes a supplier). A partly comparable benchmark never enters a range once a real offer is on file; "lowest nominal quote" needs two comparable offers, and "lowest true cost" stays not available.
- Closing the cycle (`rfq-spec.ts`, `true-cost.ts`, pure, tested): (1) what goes to an alternative supplier is the product's neutral name, specification, application and data sheet (`products.rfq_name`, `technical_specifications`, `application`, `product_documents`) — never the invoice name when it carries the current supplier's name or code; a product that can't be described in neutral words is "not ready" and no request can be prepared for it; nothing technical is ever filled in by the app. (2) A market range is a range of quotes: none → not available, one → "1 quote received", two or more comparable → range; benchmarks and trade data are shown apart, each with its own gap, and never averaged with quotes (`MarketRange.kind`). (3) True cost is computed from a quote plus inputs kept in `true_cost_scenarios` (inputs only — the result is derived): each component carries its basis, a required component nobody gave makes the result incomplete with no total, an unknown Incoterm is a warning and low confidence; the rates come from Settings or, declared as assumptions, from `SOURCING_CONFIG`. `estimatedTrueCost` of the older comparison engine stays null: true cost lives here. (4) Three words, never mixed: theoretical opportunity (benchmark or nominal prices), opportunity to validate (real quote, complete true cost, something still open), validated opportunity (also the specification confirmed by the user). "Saving" is what an invoice proves and is not computed. "Lowest quote" and "lowest estimated true cost" are stated apart and need two comparable offers. (5) `readReply` settles a number that can be read two ways only when the price paid today makes one reading absurd; several prices that can't be assigned stay empty. (6) The live pilot is the set of products with `products.in_pilot`; until the user chooses, the largest by spend stand in. (7) A benchmark about a month takes that month's average exchange rate (`period_month`, `fx_method`).
- Negotiation intelligence (`src/lib/negotiation/`, pure, tested; `src/server/negotiation.ts`; the card on the product page, one line on the market page, a list on Opportunities): for one product and this buyer, an achievable price range, a suggested target inside it, a confidence and the reasons. Rules that must hold: (1) it is an estimate and says so — never a market price, a quote or a saving; what the target is worth is a "potential negotiation upside", always theoretical: "validated" comes only from a real quote's true cost (`true-cost.ts`), a saving only from an invoice; (2) the range is anchored on price evidence, never on a percentage of the current price: real offers on true cost set both ends (one offer moves the cautious end halfway until a second confirms it), published references are counted for a part of their distance (weights in `NEGOTIATION_CONFIG`) scaled by the buyer's negotiation strength, and the cautious end goes above today's price only by a share of the rise the buyer's own invoices show; a quoted price whose true cost is incomplete counts for half, with a warning; a published reference never overrules a real offer; (3) with no evidence able to stand on its own (the buyer's invoices alone, border averages under a customs code nobody confirmed, system estimates) there is no range: "not enough data", and what to get — nothing is estimated in its place; (4) the buyer's negotiation power is six scores read from what is on file, weighted by the kind of product (`profileOf`: commodity, standard, custom, packaging, other — from the research class and the catalogue kind, never from a company's own categories); they are shown in words, never as figures. The buyer's own leverage is made of the product's volume, the usual order size, whether orders could be grouped or committed, and the supplier relationship leverage (`relationship.ts`): everything bought from the supplier, read from the invoices as five scores (total spend, cross-category spend, breadth, regularity, bundle potential). Spend is never counted twice: cross-category spend is the supplier's total minus this product, and the buyer's power takes from the relationship only what lies beyond the product's own volume. It is leverage, never a discount: more products bought move the power, not a price by themselves, and real offers still set the range. Nothing on file knows the supplier's side, so until the user says how much the company matters to the supplier (`buyer_importance`) the relationship score is capped and its confidence held down; its figure out of ten is shown only in the leverage analysis, next to the facts and thresholds it comes from; (5) every input shows its status (confirmed, estimated, missing), source and method, taken from the product dataset wherever the field lives there; what a person knows better than the rules (switching difficulty, standardization, criticality, the buyer's importance to the supplier) is kept in `product_data_fields` with its reason and the software's own estimate, and wins over the rules; (6) figures are given at three significant figures of the price paid (`precisionOf`) — no false precision; (7) the estimate is always worked out fresh from the evidence: `negotiation_estimates` only keeps what was said each time the visible answer changed (`history.ts`; written once the response is out, after every action and after a product page is shown — `keepEstimateHistory`); (8) every price the engine uses carries a data class (`data-class.ts`): purchase prices, quotes, estimates and targets are private to the account that owns them; only what a supplier publishes itself and aggregate benchmarks are public — `publicView` is all that may ever be shown about a stored estimate outside its account. Nothing here writes a price, a quote or a supplier.
- Supplier entity resolution (`src/lib/suppliers/resolve.ts`, pure, tested; `src/server/suppliers.ts`; the suppliers page and each supplier's page): the same company written in several ways is read as one. Rules that must hold: (1) the hierarchy is VAT number, tax code, web domain, the same normalized name (`companyKey`), a similar name — with phone and city only as support. A name alone never proves anything, and two different VAT numbers are two legal entities whatever their names say; (2) a merge is a pointer (`suppliers.merged_into_id`), never a rewrite: the merged record keeps its name, its purchases and its quotes, every read goes through `canonicalIds` (`readDataset`, `readLearning`, `readSourcing`), and taking a merge back is clearing the pointer. No purchase's supplier is ever changed; (3) records are merged without asking only on a strong identifier (`automatic`: the same VAT number or tax code, or the same domain with names that agree) — `autoMergeSuppliers`, run after the writes that may create a supplier. Everything else is a suggestion the user merges or keeps separate; what was decided lives in `supplier_resolutions` (history, undo, the pairs not to propose again), and a merge taken back is never made again by itself; (4) the names a document wrote are never lost: they stay on `import_items`, on the merged records and in `supplier_aliases`, and `supplierIdentity` lists them with how each line was tied to the company; (5) imports match with the same hierarchy (`matchSupplier`): VAT number and tax code first, a name written on a merged record leads to the company it is read as, and the same name with a different VAT number is a question, not a match; (6) no language model is called: rules decide what is proposed, identifiers what is merged. Code that takes a supplier id from a raw row (a purchase, a candidate, a product's current supplier) resolves it with `canonicalSupplierId` / the `canon` map first. The supplier relationship leverage is read on the canonical supplier.
- Sourcing strategy (`src/lib/portfolio/`, pure, tested; `src/server/portfolio.ts`; the page `/strategy`): for the products that weigh most (`PORTFOLIO_CONFIG.rounds`), today's mix of suppliers and the mix that would do best on one objective at a time — lowest cost, bundle, specialists, total economic value, quality, delivery, risk, cash flow, fewer suppliers, balanced, custom weights. Rules that must hold: (1) there is no supplier that is right for everything and nothing here chooses one: a mix is something to examine, "evaluate a switch" is the strongest thing said, and nothing is written — the objective, the weights and the limits travel in the page's address (`params.ts`); (2) a product is given only to a supplier with a price for this buyer — the price paid or a real offer (true cost when complete; a quoted price whose true cost is incomplete is theoretical and stays out of "total economic value"). A candidate nobody asked is counted as possible coverage, never allocated and never compared; (3) every mix is read as its advantage over today's, criterion by criterion (`advantages`): what is not on file gives no advantage, so a supplier is never preferred on a lead time, a payment term or a quality nobody wrote down, and an objective whose own data is missing says "not enough data" with what to collect — quality has no record in the database yet and is never scored; (4) coverage is weighed by spend, not by the number of products, and is a bonus next to the cost (weights in `PORTFOLIO_CONFIG`), never a winner by itself; a single-product supplier is judged on its product and is never penalised for covering one; (5) consolidation is leverage and dependence at once: every mix shows its concentration and a risk read from dependence, single sources, suppliers never bought from and distance; a heavy product can be shared between two suppliers (`dualSplit`); (6) an advantage is what the prices on file say, split by what stands behind it (theoretical, to validate, validated — `true-cost.ts`'s words) and never called a saving; the negotiation upside with the suppliers that stay is shown apart and never added to it; what one more supplier costs to manage is valued only when the user says it; (7) limits the user sets (share, number of suppliers, lead time, area, suppliers to leave out, products to keep, two sources for critical products) are respected or said to be impossible on the data on file — never silently dropped. Who could take several products of the same supplier at once also reaches negotiation intelligence (`competition.bundle`): a reason and a small bonus, still "on paper" until a real offer.
- New migrations are applied by the running dev server (`getDb()` re-checks the journal): back up `.data` before generating one on a machine with real data.
- Every description found on a document is kept as an alias (`product_aliases`: as written, per supplier, with supplier code, EAN, confidence, confirmation and source import) through `saveAlias()`; aliases of spend items are only recognised for their own supplier.
- Lines that are not purchases (credit notes, zero amounts) carry an issue with `excludes: true` and are set aside (`skipped`) by `evaluateItems`, with the reason; bringing one back acknowledges it. Line identity for duplicates includes the invoice line number when the file has one.
- Electronic invoices (FatturaPA XML, also signed `.p7m`) are read field by field in `src/lib/import/extract/einvoice.ts` / `p7m.ts`: nothing is interpreted, and the signature is not verified.
- Zip files are opened in the browser (`src/lib/import/archive.ts`) and each file inside goes through `createUpload` like a file dropped on its own; the server never receives a zip. What can't be read (unknown type, password, damage, over 20 MB) is listed to the user with the reason, never skipped silently. The accepted extensions and the size limit live in `src/lib/import/files.ts`, shared by browser and server.
- Company settings (`settings` table, one row: name, country, VAT number, user name) are read with `getSettings()`; they are not purchasing data and survive "Clear all data". `src/lib/config.ts` only holds the defaults.
- Procurement product dataset (`src/lib/dataset/`, pure, tested; `src/server/product-data.ts`; panel on the product page, `/products/data` for the priority products): every field of a priority product (`fields.ts`) is confirmed (a document, a person, or plain arithmetic on invoices: a sum, the lowest price), estimated (an inference: median as typical order, a year annualized from a shorter history — always labelled, with its method) or missing — never filled in. Values live where the app already reads them (neutral name, specification and application on `products`, structured specs in `products.specs`, payment terms on the supplier, minimum order and lead time on `supplier_products`); `product_data_fields` keeps who wrote each one and when, the estimate it replaced, and the values with no other home (delivery basis, freight, confirmed volumes, quality notes). Confirmed volumes are used first by requests, research and the true cost (`server/confirmed.ts`). Sourcing readiness is `rfq-spec.ts`'s verdict; true cost readiness is judged apart and never blocks sourcing. The priority list and its order are the existing Pareto; the first round is `DATASET_CONFIG.topProducts`. The CSV export (`/export/product-dataset`) is a copy: the database stays the source of truth.
- Visual identity: dark navigation rail (`night` tokens), `ledger` blue for primary actions, colour only for meaning. A percentage or score shown to the user must be a real, explainable ratio (the "Data status" ring is products-with-a-comparison ÷ products).
